# Database: schema, migrations, raw-SQL constraints

- `schema.prisma` — tables, enums, ordinary indexes and FKs (PLAN.md section 3).
- `migrations/` — applied in order by `prisma migrate deploy`.
  - `*_init` — generated by Prisma from the schema.
  - `*_db_constraints` — **hand-written SQL** for rules Prisma's schema language cannot express.
- `seed.ts` — idempotent development data (`pnpm --filter @ticketify/api db:seed`).

## Hand-written constraints

| Name | Table | Rule |
|---|---|---|
| `btree_gist` (extension) | — | Lets one GiST index mix `=` on `room_id` with range `&&` |
| `showtimes_time_range_check` | `showtimes` | `ends_at > starts_at` |
| `showtimes_no_overlap` | `showtimes` | `EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&) WHERE status <> 'CANCELLED'` — half-open, so back-to-back showtimes are allowed |
| `showtime_seats_available_check` | `showtime_seats` | `AVAILABLE ⇒ booking_id IS NULL` |
| `showtime_seats_held_check` | `showtime_seats` | `HELD ⇒ booking_id IS NOT NULL AND held_until IS NOT NULL` |
| `showtime_seats_sold_check` | `showtime_seats` | `SOLD ⇒ booking_id IS NOT NULL` (a sold seat always traces back to the paying booking) |
| `tickets_showtime_id_seat_id_live_key` | `tickets` | `UNIQUE (showtime_id, seat_id) WHERE status <> 'VOID'` |
| `payments_booking_id_success_key` | `payments` | `UNIQUE (booking_id) WHERE status = 'SUCCESS'` |

Also relevant, but declared in `schema.prisma` (so Prisma manages them):

- `payments_vnp_transaction_no_key` — plain `UNIQUE (vnp_transaction_no)`. Postgres' default `NULLS DISTINCT` lets any number of rows have `NULL`. VNPay may send the same placeholder number (e.g. `"0"`) for failed/cancelled attempts; phase 3 must only store a value that is unique per real transaction (to be checked against the sandbox).
- `outbox_events_status_next_retry_at_idx` — `(status, next_retry_at)`. It is a plain index, so it lives in the schema: if it were only in raw SQL, Prisma would see it as drift and generate a `DROP INDEX`.

Every rule above is exercised by `test/integration/db-constraints.int-spec.ts` (one rejected and one accepted case each).

When the application catches violations, map them by **constraint name** (e.g. `showtimes_no_overlap` → `409`).

## Does Prisma drift on these? (verified with Prisma 7.10.1)

Prisma's migration engine does not model exclusion constraints, CHECK constraints or (without the `partialIndexes` preview feature) partial indexes, and it **ignores** them when diffing. Verified after applying both migrations:

```bash
cd apps/api
# Live DB vs schema → must print "-- This is an empty migration."
pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script
# Must create an empty migration (delete it afterwards)
pnpm exec prisma migrate dev --create-only --name drift_probe
```

Both are empty. Adding unrelated indexes to `tickets`, `payments` and `showtimes` produced only `CREATE INDEX` statements, never a `DROP` of the constraints above.

## Rules

1. **Never use `prisma db push`** against a real database: it skips migration files, so none of the constraints above would exist.
2. **Do not enable the `partialIndexes` preview feature** without also declaring the two partial unique indexes in `schema.prisma` with exactly the same names and predicates; otherwise Prisma will start diffing them and generate `DROP INDEX`.
3. Changing one of these constraints = a **new** hand-written migration (`prisma migrate dev --create-only --name <name>`, then write SQL). Never edit an applied migration.
4. After any schema change, run the two drift commands above; the CI integration tests also fail if a constraint disappears.
5. `prisma db pull` does not round-trip these constraints; do not regenerate the schema from the database.
